# レポートの書式

ローカルに書き出すレポートの構成。見出しの順番は固定し、該当がない節は「なし」と書いて残す（再診断で比較しやすくするため）。リンクは必ず完全な URL で書く。秘密情報の値は書かない。

````markdown
# セキュリティ対策状況 診断レポート

| 項目 | 内容 |
|---|---|
| 対象 | `owner/repo`（ブランチ `main`、コミット `abc1234`） |
| 診断日 | YYYY-MM-DD |
| 診断方法 | リポジトリの静的調査（コード・設定・CI・依存関係）。collect_signals.py 1.x ＋ コードの目視確認（使った追加ツールがあれば版も） |
| 適用した基準 | OWASP ASVS 5.0.0 / OWASP Top 10:2025 / …（実際に使ったものだけ） |
| プロジェクトの種類 | 例: Express の REST API、Docker、GitHub Actions |
| 前提 | 例: インターネット公開・個人情報あり（README から推定）。推定したものは推定と書く |

## 8. 診断の範囲と限界
- リポジトリの静的な調査であり、ペネトレーションテストや本番環境の検査ではない
- 見つからなかったことは、脆弱性がないことの証明ではない
- ASVS の全要件（5.0.0 で 345 件）ではなく主要な項目を抜粋して評価した。ASVS への準拠を示すものではない
- 調べられなかったこと（例: 依存関係の脆弱性照会はネットワークを使うため未実施）
````

## 書き方のポイント

- 「引っかかった理由」は、読んだ人がその場所を開いて同じ判断ができる具体さで書く。パターン一致だけで判断した項目はそう書き、確信度を下げる。
- 「放置した場合のリスク」は、チェック項目のリスク文をこのプロジェクトの資産（扱うデータ、公開範囲、使っているクラウド）に当てはめて書く。脅すような誇張はしない。
- 対応済みの項目も必ず載せる。できていることが分かると、次に何をすべきかの判断材料になる。
- 付録 A には、適用したすべての項目（対象外を含む）を ID 順に並べる。
