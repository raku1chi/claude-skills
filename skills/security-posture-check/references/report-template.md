# レポートの書式

ローカルに書き出すレポートの構成。見出しの順番は固定し、該当がない節は「なし」と書いて残す（再診断で比較しやすくするため）。リンクは必ず完全な URL で書く。秘密情報の値は書かない。

同じ内容を二度書かないこと。証拠とリスクは「4. 指摘の詳細」に、手順と完了条件は「3. 対応方針」に書き、互いに ID で参照する。

````markdown
# セキュリティ対策状況 診断レポート

> 取り扱い注意: 未修正の脆弱性の場所が書かれている。公開リポジトリにはコミットしない（`.gitignore` に追加するか、リポジトリの外に保管する）。

| 項目 | 内容 |
|---|---|
| 対象 | `owner/repo`（ブランチ `main`、コミット `abc1234`） |
| 診断日 | YYYY-MM-DD |
| 診断方法 | リポジトリの静的調査（コード・設定・CI・依存関係）。collect_signals.py 1.x ＋ コードの目視確認（使った追加ツールや、行った再現があればその内容も） |
| 適用した基準 | OWASP ASVS 5.0.0 / OWASP Top 10:2025 / …（実際に使ったものだけ） |
| プロジェクトの種類 | 例: Express の REST API、Docker、GitHub Actions |
| 前提 | 例: インターネット公開・個人情報あり（README から推定）。推定したものは推定と書く |
| 対象外の領域 | 例: LLM（LLM を呼ぶコードなし）、CTR・IAC（コンテナ定義なし） |

## 前回からの変化
（再診断のときだけ。改善した項目 / 悪化した項目 / 新しく見つかった項目）

## 1. 総評
3〜5 行。最大のリスクと、できている点の両方。原因の数で語る（例:「Critical の原因は 3 つ」）。

## 2. スコアカード

| 領域 | ✅ 対応済み | 🟡 一部対応 | ❌ 未対応 | ❓ 要確認 | ➖ 対象外 |
|---|---|---|---|---|---|
| GOV 開発プロセス | | | | | |
| … | | | | | |
| **合計（適用した n 項目）** | | | | | |

重大度の内訳（原因＝対応項目の単位）: Critical n / High n / Medium n / Low n

## 3. 対応方針（優先度順）

| ID | 対応項目 | 優先度 | 重大度 | 工数 | 関連するチェック |
|---|---|---|---|---|---|
| R-01 | 漏えいした秘密情報を失効・ローテーションし、設定から除去する | P1 | Critical | M | SEC-01, SEC-02, SEC-03 |

すぐできる改善（優先度が高く工数 S）: R-02, R-03

### R-01 <対応項目のタイトル>（P1 / Critical / 工数 M）
- **目的**: 何のリスクを消すのか（1 文。詳細は関連するチェックの指摘を参照）
- **手順**:
  1. このコードベースに即した具体的な手順（ファイル名・関数名・設定例）
  2. …
- **完了条件**: どう確かめれば完了か（テスト、確認コマンドなど）
- **参考**: 手順に直接役立つリンク 1〜2 個

## 4. 指摘の詳細（❌・🟡 のうち Medium 以上）

領域ごとに、重大度の高い順に並べる。1 項目 4 行程度:

#### ❌ SEC-01 現在のファイルに秘密情報が含まれていない — Critical（確信度: 高）→ R-01
- **理由**: `src/config.js:4` に AWS のアクセスキー ID（`AKIA...(20 chars)`）とシークレットキーが直書きされている。形式が本物のキーと一致し、テスト用の値ではない
- **放置した場合のリスク**: このリポジトリを読める人は誰でもこの鍵で AWS を操作できる。請求書バケットのデータ持ち出しや、不正なリソース作成による高額請求が起こりうる
- **根拠**: CWE-798 https://cwe.mitre.org/data/definitions/798.html / ASVS v5.0.0-13.3.1 (L2) https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md / OWASP Top 10:2025 A07 https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/

## 6. 診断の範囲と限界
- リポジトリの静的な調査であり、ペネトレーションテストや本番環境の検査ではない
- 見つからなかったことは、脆弱性がないことの証明ではない
- ASVS の全要件（5.0.0 で 345 件）ではなく主要な項目を抜粋して評価した。ASVS への準拠を示すものではない
- 調べられなかったこと（例: 依存関係の脆弱性照会はネットワークを使うため未実施）
````

## 書き方のポイント

- 「理由」は、読んだ人がその場所を開いて同じ判断ができる具体さで書く。パターン一致だけで判断した項目はそう書き、確信度を下げる。重大度を既定値から変えたら、その理由もここに書く。
- 「放置した場合のリスク」は、チェック項目のリスク文をこのプロジェクトの資産（扱うデータ、公開範囲、使っているクラウド）に当てはめて書く。脅すような誇張はしない。
- 対応済みの項目も必ず載せる。できていることが分かると、次に何をすべきかの判断材料になる。
- 付録 A には、適用した領域のすべての項目を ID 順に並べる（領域ごと対象外にしたものは載せない）。
