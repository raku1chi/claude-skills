# オープンデータでアプリを考える

アプリのアイデア出しと、作りたいアプリに使えるデータ探しを手伝う。根拠にするのは、日本の公的機関を中心に海外の主要なものも含めたオープンデータ・公開 API のカタログ（約 190 件、2026 年 10 月時点）で、データごとに形式・登録の要否・商用利用の可否と、提供終了や規約・法令の注意点が調べてある。

返答の言語はユーザーに合わせる（既定は日本語）。

## 原則

この分野では 2024〜2026 年に提供終了・有料化・規約の変更が相次ぎ、よく知られた API がもう使えないことが多い（例: RESAS-API は 2025 年 3 月に終了）。だからカタログを記憶より優先し、次の点を守る。

1. **データの名前・URL・条件は、カタログか実際に開いた公式ページから引く。** 記憶で書かない。カタログにないデータを挙げるときは「カタログ外」と明記し、確かめていない条件は「要確認」とする。
2. **「使えるか」を 3 点で示す。** 登録（API キー・申請の要否）、商用（可／条件付き／不可）、形式（API／ファイル／地図タイル）。そこに、そのアプリで効く注意点を添える。
3. **終わったもの・公開するアプリで使えないものを勧めない。** 下の「よくある落とし穴」と、カタログの各表の下にある注記を確かめる。終了・移行・制限は注記に書いてあることが多い。
4. **調べた時点を示す。** 今日の日付を調査時点（2026 年 10 月）と比べ、半年以上たっていれば冒頭でそう伝える。Web を見られるなら、勧める本命のデータ（1〜3 件）の公式ページで提供状況と規約を確かめ、確かめた日付を書く。アイデア出しの段階ではそこまでせず、時点を書いて進めてよい。
5. **法令・規約の説明は一般的な情報で、法的な助言ではない。** 商用でリリースするかの判断が絡むときは、その旨を一言添える。

## 表の読み方

カタログの表は 1 行が 1 データで、列は次のとおり。

| 列 | 意味 |
|---|---|
| データ（提供元） | 名称と提供元。リンク先が公式ページ |
| 中身 | アプリで取れる情報の要点 |
| 形式 | API／ファイル（CSV・GeoJSON・XML など）／地図タイル |
| 登録 | API キーの発行や利用申請が要るか |
| 商用 | 可: 出典表記など一般的な条件だけ／条件付き: 規約に追加の制限がある／不可。「要確認」「データごと」「記載なし」は、調査で確定できなかったもの |
| 使いどころ | 作れるアプリの例 |

表の下の箇条書き（注記）に、終了・移行・規約の細かい条件が書いてある。データを勧める前に、その行だけでなく注記も読む。

## 進め方

### 1. 依頼の種類を見分ける

| 種類 | 例 | 進め方 |
|---|---|---|
| アイデア出し | 「防災で何か作れない？」「e-Stat を使って何か作りたい」「ハッカソンのネタがほしい」 | 手順 2 → 3A |
| データ探し | 「近くの開いている小児科を探すアプリに使えるデータは？」 | 手順 2 → 3B |
| 条件の確認 | 「OSM は商用で使える？」「法人番号の API は登録が要る？」 | 該当する行と注記、licenses-and-legal.md を引いて短く答える |
| 具体化 | 「2 番目の案を詳しく」「データの取り方を設計して」 | 3B に、取得・更新・表示の設計を足す（出力の形の「具体化」） |

### 2. 前提を置き、カタログを引く

最初に質問を重ねない。会話から前提を読み取り（リポジトリの中で頼まれたら、README や package.json などから構成も読む）、分からない点は次の既定で進めて、出力の冒頭に 1 行で書く。

- **公開範囲**: 一般に公開するアプリ（商用の可能性あり）として判定する。個人用・社内用・研究用と分かっていれば、非商用に限られたデータ（Open-Meteo の無料版など）も候補にしてよい
- **地域**: 日本全国。特定の地域なら、その都道府県・市区町村のデータも探す（portals.md）
- **構成**: サーバーのある Web アプリ。ブラウザだけで動かしたいなら、登録不要でブラウザから直接呼べる（CORS 対応の）API や配布ファイルを優先する

「データの地図」で関係する分野を選び、そのファイルを読む（たいてい 2〜4 個）。キーワードで探すなら、このスキルの `references/catalog/` を検索する（例: `避難|AED`、`GTFS`、`法人番号`）。表の行と注記の両方がヒットする。商用利用・クレジット表示・法令が絡むなら licenses-and-legal.md を、アイデア出しなら idea-patterns.md も読む。

### 3A. アイデアを出す

idea-patterns.md の「共通キー」「発想の型」「組み合わせの例」を使う。各表の「使いどころ」列も小さなアイデアの種になる。

- 既定は 5 案。定番の組み合わせと、分野をまたぐ意外な組み合わせを混ぜ、発想の型が偏らないようにする。
- 1 つのデータを眺めるだけのアプリは、公式サイトや既存のサービスと変わらなくなりがち。共通キーで 2〜3 種類のデータをつなぎ、使う人の状況（住所、通勤経路、取引先、子どもの年齢など）に合わせると価値が出る。
- 案ごとに「誰の何を解決するか」を具体的に書く。
- 作りやすさは、登録・審査の手間、商用の条件、サーバーの要否、データの形（API か、PDF や自治体ごとにばらばらのファイルか）で判断する。

起点がデータのとき（「e-Stat で何か作りたい」）は、そのデータの「使いどころ」と、共通キーでつなげられる相手から発想する。

### 3B. データを選ぶ

アプリを機能に分け、機能ごとに使うデータを決める。

- 機能ごとに本命を 1 つ選び、代わりの候補とは分けて示す。
- 同じ情報が複数あるときは、公式で継続性があるもの、試験公開・コミュニティ運営のもの、非公式のものの順に優先する。一般に公開するなら「商用: 可」を優先し、条件付きなら条件を書く。
- カタログで見つからない機能は「公開データが見つからない」と正直に書き、代わりの手段を挙げる（portals.md や global.md の「データを探す場所」で探す、OpenStreetMap などの共同編集データ、自治体のデータ、ユーザーの投稿、有料のサービス）。Web を検索できれば探してよいが、見つけたものは「カタログ外」とし、確かめた条件だけを書く。

### 4. 返す

下の「出力の形」に沿ってチャットで返す。ファイルへの保存は頼まれたときだけにする。最後に、結果をいちばん大きく変える質問を 1〜2 個だけ添える（例: 商用で出すか、対象の地域、スマホアプリか Web か）。

## よくある落とし穴

### 終わった・移ったもの

| 勧めないもの | 代わり |
|---|---|
| RESAS-API（2025-03-24 終了）、V-RESAS（2024-03 終了） | e-Stat API などの元の統計 |
| 土地総合情報システム（2024-03 末に廃止） | 不動産情報ライブラリ |
| EDINET API v1（2024-03 終了） | EDINET API v2（API キー必須） |
| 気象庁 HP の内部 JSON（非公式。2026-05 に警報のパスが変わった） | 気象庁防災情報XML |
| 地理院地図の住所検索・逆ジオコーダ（公開 API ではない） | ABRジオコーダー（v3）、normalize-japanese-addresses |
| 駅データ.jp の無料 API（2020 年に停止） | 国土数値情報（駅） |
| REST Countries の無料利用（2026-04 の v5 でキー必須、無料は非商用のみ） | 国の基本情報は Wikidata（CC0） |

ほかにも J-Quants V1、海しるAPI v2（2027 年末で終了）、ABRジオコーダー v2、シェアサイクル kotobike の GBFS などの終了・移行が、各ファイルの注記にある。

### 公開するアプリでは使えない・制限が強いもの

- **J-Quants**（株価）: 第三者への提供が規約で禁止。自分専用の分析にとどめる。TDnet（適時開示）にも無料の API はない
- **全国AEDマップ**: 許諾のない二次利用は禁止。自治体が公開する「AED 設置箇所」のデータを使う
- **Open-Meteo の無料版**、**OpenSky Network**: 非商用のみ
- **OpenStreetMap の公式タイル・Nominatim・Overpass の公開インスタンス**: 軽い利用だけ。商用の本番では自前で立てるか、商用の提供者を使う
- **文化遺産オンライン**（転用禁止）、**強震モニタ**（転載・再配布禁止）、**官報**（自動巡回禁止）、**川の水位**（公開 API なし）
- **インボイスの公表情報**: 個人事業者の情報を名簿や検索サービスにしない（個人情報保護法に触れるおそれがあり、規約でも目的外の第三者提供を禁止）
- 条件付きの例: 日銀 API（商用目的の転載は事前相談、改変不可）、UN Comtrade（原則として内部利用）、WHO GHO（商用は事前許可）、PMDA の添付文書（巡回取得禁止）、特許情報取得 API（産業財産権に関する目的に限る）、ハローワーク求人 API（職業紹介事業者などに限る）、メッシュ農業気象データ（作った情報の販売は不可）

### 作るときに詰まりやすいところ

- **申請に時間がかかる**: 法人番号・インボイスの Web-API は、アプリケーション ID の発行に 2 週間〜1 か月。不動産情報ライブラリの API キーは審査制。早めの申請を勧める
- **ブラウザから直接呼べない**: 不動産情報ライブラリの API はサーバー経由で使う。ブラウザだけで作るなら、統計ダッシュボードAPI（登録不要・CORS 対応）、地理院タイル、配布ファイルが向く
- **キーの置き場所**: API キーやアプリケーション ID はブラウザやスマホアプリに埋め込まず、サーバー側に置く（国税庁の API は ID の開示を、e-Stat は譲渡・貸与を禁止）
- **ID や仕様が変わる**: e-Stat の統計表 ID は基準改定で変わる（消費者物価指数は 2026-08 から 2025 年基準）ので、直書きせず検索 API か設定ファイルで持つ。2026-05-29 から警報がレベル付きの新体系になり、XML 電文も増えた
- **試験公開・非公式**: 地理院の標高 API とベクトルタイルは試験公開、P2P地震情報はコミュニティ運営。止まる前提でキャッシュと監視を用意する
- **データの形**: ハザードマップのタイルは画像なので、地点が区域に入るかの判定は国土数値情報のベクトルデータで行う。自治体のデータは列名も更新頻度もばらばらなので、自治体標準オープンデータセットの項目にそろえる。祝日 CSV は UTF-8 ではない
- **更新が止まっている**: 全国の人流オープンデータ（2019〜2021 年）、女性の活躍推進企業データベース（最終更新 2025-07）、5374（2022-07 にアーカイブ）

### ライセンスと法令（詳しくは licenses-and-legal.md）

- 国の新しいデータの多くは公共データ利用規約（PDL1.0）か CC BY 4.0 で、出典を書けば商用でも使える
- CC BY-SA（Wikipedia、JMdict、CODH など）と ODbL（OpenStreetMap、Open Food Facts など）は、加工して配るデータに同じライセンスが及ぶ。アプリのコードと配るデータは分けて考える
- e-Stat・統計ダッシュボード・法人番号・インボイス・不動産情報ライブラリ・日銀・海しる・交通量 API・J-STAGE・OpenStreetMap は、アプリ内にクレジット表示が要る（文言は公式ページのものを使う）
- **気象業務法**: 気象庁の予報をそのまま見せるのは自由だが、独自の予報（機械学習を含む）には予報業務許可が要る。自前の通知を「警報」と名付けない
- **測量法**: 地理院タイルを URL から読み込むなら出典の明示だけでよいが、保存して同梱・配布するなら承認が要ることがある
- **スクレイピング**: EDINET とインボイス公表サイトは規約で禁止。公式の API か配布データを使う

## 出力の形

データ名には公式ページへのリンクを付ける（カタログのリンクを使う）。前提と調査時点は冒頭に 1 行で書く。

### アイデア出し

```markdown
前提: 一般公開の Web アプリ（商用の可能性あり）、日本全国。データは 2026 年 10 月時点の調査にもとづく。

### 1. 〈仮の名前〉— 〈一言で〉
- **誰の何を解決するか**: …
- **使うデータ**: [データ名](公式URL)（提供元）＋[データ名](公式URL)（提供元）。つなぐキー: …
- **できること**: …
- **作りやすさ**: すぐ試せる／準備が要る／ハードルが高い（理由: …）
- **注意**: いちばん効く 1〜2 点

（2〜5 も同じ形）

| 案 | 作りやすさ | 要る登録 | 商用 | いちばんの注意 |
|---|---|---|---|---|
```

作りやすさの目安:

- **すぐ試せる**: 主なデータが登録不要か無料ですぐ使え、商用可で、API か整ったファイルで取れる
- **準備が要る**: 申請・審査、サーバー、データの整形や結合のどれかが要る
- **ハードルが高い**: 許諾・契約が要る、データが PDF や自治体ごとにばらばら、法令の制約が大きい

最後に「気になる案があれば、データの取り方・つなぎ方・申請の段取りまで具体化する」と添える。

### データ探し

```markdown
**結論**: 〈核になる機能〉は [本命のデータ](公式URL)（提供元）で取れる。〈補助の機能〉は [データ名](公式URL) を組み合わせる。
前提: …／2026 年 10 月時点の調査

| 機能 | データ（提供元） | 形式 | 登録 | 商用 | メモ |
|---|---|---|---|---|---|

**注意すること**（このアプリに効くものだけ）
- …

**公開データが見つからない部分**
- 〈機能〉: 〈現状〉→〈代わりの手段〉

**次の一歩**
1. 時間のかかる申請を先に
2. …
```

### 具体化（データの設計）

データ探しの形に次を足す。長くなるなら、ファイルに保存するか聞く。

- **つなぎ方**: どのキーで、どの順に変換・結合するか
- **取得と更新**: API を都度呼ぶか、一括ダウンロードして持つか。更新の頻度（データの更新頻度に合わせる）とキャッシュ
- **表示の義務**: クレジットの文言と置き場所、ライセンスの表記、継承が及ぶデータの扱い
